# 读写分离与分库分表设计方案

> 基于 Spring Boot + MyBatis 架构的实践经验总结。

---

## 一、读写分离适用场景

读写分离用**一个主库**写、**多个只读副本**读，适合读多写少的业务。

### 1. 读远多于写的业务
- 内容展示类系统（CMS、新闻、博客、文档站点）
- 电商商品浏览、店铺信息
- 用户个人信息页、动态流

### 2. 报表与统计分析
- 数据仓库查询
- BI 报表、日志分析、大屏展示
- 避免复杂读查询影响在线写入

### 3. 高并发查询
- 搜索服务、推荐系统
- 微服务中大量读接口
- API 网关后的频繁数据读取

### 4. 数据备份与故障切换
- 从库既做副本也可以对外提供读服务
- 减轻主库压力，提高整体 QPS

### 核心思想
- **主库** 负责写入、更新、删除
- **从库** 负责查询
- 通过数据同步（如 MySQL 主从复制）保持副本一致

> ⚠️ 不适合写入密集或实时一致性要求极高的业务。

## 二、Spring Boot + MyBatis 读写分离实现

### 2.1 多数据源配置（application.yml）

```yaml
spring:
  datasource:
    master:                          # 主库（写）
      jdbc-url: jdbc:mysql://master-host:3306/db
      username: root
      password: xxx
      driver-class-name: com.mysql.cj.jdbc.Driver
    slave:                           # 从库（读）
      jdbc-url: jdbc:mysql://slave-host:3306/db
      username: root
      password: xxx
      driver-class-name: com.mysql.cj.jdbc.Driver
```

### 2.2 数据源配置类

```java
@Configuration
public class DataSourceConfig {

    @Bean
    @ConfigurationProperties("spring.datasource.master")
    public DataSource masterDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    @ConfigurationProperties("spring.datasource.slave")
    public DataSource slaveDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    public DataSource routingDataSource() {
        Map<Object, Object> targetDataSources = new HashMap<>();
        targetDataSources.put(DataSourceType.MASTER, masterDataSource());
        targetDataSources.put(DataSourceType.SLAVE,  slaveDataSource());

        DynamicDataSource dataSource = new DynamicDataSource();
        dataSource.setDefaultTargetDataSource(masterDataSource());  // 默认走主库
        dataSource.setTargetDataSources(targetDataSources);
        return dataSource;
    }
}
```

### 2.3 动态数据源 — AbstractRoutingDataSource

```java
public class DynamicDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return DataSourceContextHolder.get();
    }
}
```

### 2.4 线程级数据源上下文

```java
public class DataSourceContextHolder {
    private static final ThreadLocal<DataSourceType> CONTEXT = new ThreadLocal<>();

    public static void set(DataSourceType type) { CONTEXT.set(type); }
    public static DataSourceType get()         { return CONTEXT.get(); }
    public static void clear()                 { CONTEXT.remove(); }
}
```

```java
public enum DataSourceType {
    MASTER, SLAVE
}
```

### 2.5 声明式注解 + AOP 切面

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface DataSource {
    DataSourceType value() default DataSourceType.SLAVE;
}
```

```java
@Aspect
@Component
@Order(1)  // 确保在 @Transactional 之前执行
public class DataSourceAspect {

    @Around("@annotation(ds)")
    public Object around(ProceedingJoinPoint point, DataSource ds) throws Throwable {
        DataSourceContextHolder.set(ds.value());
        try {
            return point.proceed();
        } finally {
            DataSourceContextHolder.clear();  // 必须清理，防止线程池污染
        }
    }
}
```

### 2.6 Service 层使用示例

#### 场景一：读写混合 → 整体走主库

```java
@Service
public class OrderService {

    @Autowired private OrderMapper orderMapper;
    @Autowired private StockMapper stockMapper;

    @Transactional
    public void placeOrder(Long productId, int quantity) {
        // 整个方法走主库（因为有写操作）
        // 不要在这类方法里混用 @DataSource
        int stock = stockMapper.getStock(productId);      // 主库读（避免主从延迟）
        if (stock < quantity) {
            throw new BusinessException("库存不足");
        }
        stockMapper.deductStock(productId, quantity);      // 主库写
        orderMapper.insertOrder(...);                       // 主库写
    }
}
```

#### 场景二：读写拆开 → 代理注入打破 this 调用

```java
@Service
public class ProductService {

    @Autowired private ProductMapper productMapper;
    @Autowired private LogMapper logMapper;
    @Autowired private ProductService self;  // 注入代理，解决 AOP 内部调用失效

    @Transactional
    public void updateAndQuery(Long productId) {
        // 写操作走主库
        productMapper.updateProduct(...);

        // 读操作走从库（不要求强一致性时）
        ProductVO product = self.readProduct(productId);  // 通过代理调用，切面生效
    }

    @DataSource(DataSourceType.SLAVE)
    public ProductVO readProduct(Long productId) {
        return productMapper.selectById(productId);
    }
}
```

### 2.7 三种混合场景处理策略

| 场景 | 策略 |
|------|------|
| **写完立即读同一数据** | 整个方法走主库（避免主从延迟导致读不到刚写的数据） |
| **写后读不相关数据** | 写走主库，读走从库（通过代理注入打破内部调用） |
| **纯读 + 纯写分离到不同方法** | 分别用 `@DataSource(SLAVE)` 和默认走主库 |

## 三、读写分离：粒度选择分析

### 3.1 各粒度方案对比

| 粒度 | 方式 | 主流程度 |
|------|------|----------|
| **Service 方法** | `@DataSource` 注在 Service 方法上 | ⭐⭐⭐⭐⭐ 最主流 |
| Mapper/DAO 方法 | 注在 Mapper 接口方法上 | ⭐⭐⭐ 有使用 |
| Mapper XML 粒度 | 根据 SQL ID 路由 | ⭐ 少见 |
| SQL 自动识别 | 解析 SQL，SELECT 走从库其余走主库 | ⭐⭐ 部分中间件支持 |
| Controller 层 | 太粗，基本不用 | ❌ 不推荐 |

### 3.2 Service 层粒度的好处

| 好处 | 说明 |
|------|------|
| **事务友好** | `@Transactional` 和 `@DataSource` 同层，不会出现事务在从库开启的错乱 |
| **业务语义清晰** | `@DataSource(SLAVE)` 一眼就知道这个方法走哪个库 |
| **Mapper 层无感知** | 同一个 Mapper 方法既可走主库也可走从库，复用性强 |
| **声明式，侵入性低** | 不写 if-else，不改 SQL，不改 XML |
| **社区生态成熟** | dynamic-datasource、baomidou 等方案默认都是 Service 层粒度 |

### 3.3 Service 层粒度的坏处及解决方案

| 坏处 | 说明 | 解决方案 |
|------|------|----------|
| **this 内部调用 AOP 失效** | `this.method()` 不经过代理，注解不生效 | 注入自身代理：`@Autowired private XxxService self;` |
| **粒度有时太粗** | 一个方法内无法同时走主库和从库 | 拆小方法 + 代理注入 |
| **基础设施泄露到业务层** | Service 需要关心数据源 | 可接受的权衡，声明式注解已经很轻量 |
| **新人不熟悉易出错** | 容易写 `this.xxx()` 不自知 | Code Review + 团队规范 |
| **读写混合方法被迫全走主库** | 读请求也打在主库上 | 能接受的主库压力，或拆分为独立方法 |

### 3.4 实践建议：混合策略

```
┌─────────────────────────────────────────┐
│ 默认情况：Service 方法加 @DataSource     │  ← 主方案
├─────────────────────────────────────────┤
│ 读写混合且写完需读回：整个方法走主库      │  ← 务实处理
├─────────────────────────────────────────┤
│ 极端读多场景：SQL 自动路由中间件兜底      │  ← 锦上添花
├─────────────────────────────────────────┤
│ 需要细粒度：拆小 Service 方法 + 代理注入  │  ← 按需使用
└─────────────────────────────────────────┘
```

> **结论**：Service 层粒度是权衡后的最佳实践——好处远大于坏处，坏处都有成熟的 Workaround，是 Spring Boot + MyBatis 读写分离方案的事实标准。

## 四、分库分表：粒度选择分析

### 4.1 核心结论

> **分库分表的主流粒度在 JDBC/数据源层（中间件代理层），而非 Service 层。**

与读写分离不同，分库分表的本质是 **SQL 路由**，和业务语义解耦。

```
分片键必须和 SQL 一起到达数据库层，才能正确路由。
```

```java
// Service 层只传 userId，不关心数据存在哪个库哪个表
userMapper.selectById(userId);
//                          ↑
//           这个 userId 传到 DAO/数据源层后，
//           由分片中间件根据 userId 算出 → 库3、表7
```

### 4.2 读写分离 vs 分库分表：粒度对比

```
┌───────────────┬──────────────────┬──────────┐
│     层级       │    分库分表       │  读写分离  │
├───────────────┼──────────────────┼──────────┤
│ Controller    │ ❌ 几乎不用       │ ❌        │
│ Service       │ ❌ 不是主流       │ ✅ 主流   │
│ DAO/Mapper    │ ⚠️ 过渡方案       │ ⭐ 可用   │
│ JDBC/数据源层  │ ✅ 绝对主流       │ ⭐ 可用   │
│ SQL 中间件代理 │ ✅ 主流（独立部署）│ ⭐ 可用   │
└───────────────┴──────────────────┴──────────┘
```

### 4.3 为什么分库分表不走 Service 层？

| | 读写分离 | 分库分表 |
|------|----------|----------|
| **路由依据** | 读 / 写（业务语义） | 分片键值（数据特征） |
| **Service 层是否有路由依据** | ✅ 知道这是"读"还是"写" | ❌ 不知道 `userId=100` 在哪个库 |
| **注解放在哪合适** | Service（把 `@DataSource(SLAVE)` 当声明式读写选择） | 数据源层（让中间件根据分片键自动算） |

如果强行把分库分表放在 Service 层（反模式）：

```java
// 反模式：Service 层手动指定分库
@Sharding(db = "ds3", table = "user_7")
public User getUser(Long userId) { ... }
```

- Service 需要知道分片算法 → 业务和基础设施耦合
- 分片规则一改（比如从 8 库扩到 16 库），所有 Service 都要改
- 失去了透明性这个分库分表最大的价值

### 4.4 JDBC 层 / 数据源层方案（绝对主流）

代表：**ShardingSphere-JDBC**、TDDL、Zebra

```
┌────────────────────────────────────┐
│ Service 层                         │
│   orderMapper.selectByUserId(100)  │  ← 无感知，无注解
└───────────────┬────────────────────┘
                │
┌───────────────▼────────────────────┐
│ MyBatis / JPA                      │  ← 无感知
└───────────────┬────────────────────┘
                │
┌───────────────▼────────────────────┐
│ ShardingSphere-JDBC（数据源代理）    │
│   - 解析 SQL                       │  ← 路由在这里发生
│   - 提取分片键 userId              │
│   - 计算：userId % 8 = 3 → 库3     │
│   - 改写 SQL → 表名加后缀          │
│   - 路由到目标库执行               │
└───────────────┬────────────────────┘
                │
        ┌───────┴───────┐
        ▼               ▼
    [库1,库2...]    [库3]  ← 实际执行
```

#### 配置示例（ShardingSphere + Spring Boot）

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..7}
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: db-inline
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: table-inline
        sharding-algorithms:
          db-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{user_id % 8}
```

业务代码完全不变：

```java
@Service
public class OrderService {
    @Autowired private OrderMapper orderMapper;

    public Order getOrder(Long userId, Long orderId) {
        // 和没分表时写得一模一样
        return orderMapper.selectByUserIdAndOrderId(userId, orderId);
    }
}
```

### 4.5 独立中间件代理方案

代表：**ShardingSphere-Proxy**、MyCat、DRDS

```
App → Proxy（独立进程）→ MySQL1 / MySQL2 / MySQL3
```

| 好处 | 坏处 |
|------|------|
| 多语言通用（Java/Go/Python 都能连） | 多一跳网络开销 |
| 对应用完全透明（像连一个 MySQL） | 需要独立运维中间件集群 |
| 运维可独立升级 | 复杂查询性能不如 JDBC 内嵌式 |

适合**多语言异构系统**或**不想引入 SDK 依赖**的团队。

### 4.6 DAO/Mapper 层方案（过渡方案，不推荐主用）

```java
@Mapper
public interface OrderMapper {

    @Sharding(key = "userId")
    Order selectById(@Param("userId") Long userId);
}
```

| 好处 | 坏处 |
|------|------|
| 对业务完全透明 | 需要自己实现分片逻辑和 MyBatis 拦截器 |
| 不依赖外部中间件 | 复杂查询（JOIN/子查询/跨片聚合）几乎没法处理 |
| | 和 MyBatis 绑定，其他数据访问框架用不了 |

> ⚠️ 只适合极简单的单表 CRUD，做不了真正的生产级分库分表。

## 五、总结对比

| 维度 | 读写分离 | 分库分表 |
|------|----------|----------|
| **主流粒度** | Service 层（`@DataSource` 注解） | JDBC/数据源层（ShardingSphere-JDBC 等中间件） |
| **路由依据** | 读 / 写（业务语义） | 分片键值（数据特征） |
| **业务代码侵入** | 轻量（一个注解） | 零侵入（完全透明） |
| **实现方式** | AbstractRoutingDataSource + AOP | 中间件代理 SQL 路由 |
| **核心原因** | Service 层知道是读还是写 | 只有 SQL + 分片键才知道数据在哪 |

### 易记口诀

> **读写分离问"读还是写"，Service 知道 → Service 层注解**  
> **分库分表问"数据在哪"，只有 SQL + 分片键才知道 → 数据源层中间件**
