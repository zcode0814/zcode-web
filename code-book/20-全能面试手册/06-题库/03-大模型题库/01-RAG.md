# 整理20道RAG面试题

下面是 20 道 RAG（Retrieval-Augmented Generation，检索增强生成）面试题，按从基础到工程落地、评估优化递进排列，并附详细答案。

**1. 什么是 RAG？它解决了什么问题？**

RAG 是一种把“检索系统”和“大语言模型生成能力”结合起来的架构。

典型流程是：

1. 用户提出问题。
2. 系统从外部知识库中检索相关文档片段。
3. 把检索结果和用户问题一起放进 Prompt。
4. LLM 基于这些上下文生成答案。

RAG 主要解决几个问题：

- 模型知识过时：LLM 训练完成后，内部知识不会自动更新。
- 私有知识缺失：企业内部文档、产品手册、数据库内容不在模型训练集中。
- 幻觉问题：让模型基于检索到的证据回答，可以降低凭空编造。
- 成本问题：相比微调，把知识放到外部检索系统中更灵活、更便宜。
- 可追溯性：可以返回引用来源，方便验证答案依据。

一句话总结：RAG 不是让模型“记住所有知识”，而是让模型“临时查资料后再回答”。

---

**2. RAG 和 Fine-tuning 有什么区别？什么时候用 RAG，什么时候用微调？**

RAG 和微调解决的问题不同。

RAG 适合解决“知识问题”：

- 需要接入频繁变化的知识。
- 需要回答企业内部文档。
- 需要返回引用来源。
- 知识量很大，不适合塞进模型参数。
- 希望随时更新、删除、替换知识。

Fine-tuning 适合解决“行为问题”：

- 固定输出格式。
- 特定语气、风格。
- 特定任务模式。
- 领域内稳定的推理方式。
- 提高模型在某类任务上的一致性。

例如：

- 公司制度问答：更适合 RAG。
- 把客服回复统一成品牌语气：可以微调。
- 医疗论文问答：更适合 RAG，因为需要引用最新文献。
- SQL 生成格式稳定化：可能适合微调或 few-shot。

实际项目中经常组合使用：

- RAG 提供知识。
- Fine-tuning 或 Prompt 约束模型的回答方式。

---

**3. 一个典型 RAG 系统由哪些模块组成？**

一个完整 RAG 系统一般包括：

1. 数据接入模块
   从 PDF、网页、数据库、Notion、Confluence、飞书、Git 仓库等来源拉取数据。

2. 文档解析模块
   提取文本、表格、标题结构、元数据、图片 OCR 等。

3. Chunk 切分模块
   把长文档切成适合检索和放入上下文的小片段。

4. Embedding 模块
   将文本片段转换成向量。

5. 向量数据库 / 检索索引
   存储向量和元数据，支持相似度检索。

6. Retriever 检索器
   根据用户问题召回相关内容。

7. Reranker 重排序器
   对召回结果进一步排序，提升相关性。

8. Prompt 构造模块
   把问题、检索内容、约束规则拼成最终输入。

9. LLM 生成模块
   基于上下文生成答案。

10. 后处理模块
   包括引用来源、格式化、敏感信息过滤、答案校验等。

11. 评估与监控模块
   监控召回质量、答案质量、延迟、成本、失败率。

**4. RAG 中为什么要做 Chunking？Chunk 太大或太小有什么问题？**

Chunking 是把长文档切成较小文本块，方便向量化和检索。

Chunk 太大：

- 向量表示会变得模糊，一个 chunk 里混合多个主题。
- 检索命中后放入 Prompt 会浪费上下文。
- 容易引入无关信息，干扰模型回答。
- 单次可放入的 chunk 数量减少。

Chunk 太小：

- 缺少上下文，模型看不懂片段含义。
- 一个概念被切碎，答案不完整。
- 检索结果碎片化，需要更多拼接。
- 向量语义不稳定。

常见策略：

- 按标题、段落、章节切分。
- 设置 chunk size，比如 300-800 tokens。
- 设置 overlap，比如 50-150 tokens。
- 对代码、表格、FAQ、法律条文使用结构化切分。

好的 chunk 应该满足：单块语义完整、主题集中、长度适中、可追溯到原文位置。

**5. 什么是 Embedding？为什么 RAG 需要 Embedding？**

Embedding 是把文本转换成高维向量的过程。

例如：

```text
"如何重置密码？" -> [0.12, -0.43, 0.88, ...]
```

向量之间的距离可以表示语义相似度。即使两个句子没有完全相同的关键词，也可能被判断为语义相近。

例如：

- “如何重置密码？”
- “忘记登录密码怎么办？”

关键词不同，但语义相似，Embedding 可以帮助检索系统找到相关内容。

RAG 使用 Embedding 的原因：

- 支持语义检索。
- 能处理同义词、近义表达。
- 比纯关键词匹配更适合自然语言问题。
- 可以对非结构化文档建立统一检索索引。

不过 Embedding 也有缺点：

- 对精确匹配不一定好，比如订单号、错误码、专有名词。
- 对长文本细节可能压缩丢失。
- 不同 embedding 模型效果差异明显。

所以工程上常用 hybrid search：向量检索 + 关键词检索。

**6. 向量数据库在 RAG 中的作用是什么？常见选择有哪些？**

向量数据库用于存储和检索 embedding 向量。

它的核心功能：

- 存储文本 chunk 的向量。
- 存储对应原文、文档 ID、标题、时间、权限等元数据。
- 根据 query 向量做相似度搜索。
- 支持过滤条件，比如只查某个项目、某个用户有权限的文档。
- 支持近似最近邻搜索，提高检索速度。

常见向量数据库：

- Milvus
- Pinecone
- Weaviate
- Qdrant
- Chroma
- Elasticsearch / OpenSearch 向量检索
- PostgreSQL + pgvector
- Redis Vector Search
- FAISS，本地向量索引库

选择时主要看：

- 数据量规模。
- 查询延迟要求。
- 元数据过滤能力。
- 运维复杂度。
- 是否需要多租户隔离。
- 是否已有 Elasticsearch 或 PostgreSQL 基础设施。

**7. RAG 中的 Top-K 是什么？如何选择 K？**

Top-K 指检索阶段返回最相关的 K 个文档片段。

例如 Top-5 表示返回相似度最高的 5 个 chunk。

K 太小：

- 可能漏掉关键证据。
- 对复杂问题覆盖不足。
- 多跳问题回答困难。

K 太大：

- 引入无关内容。
- Prompt 变长，成本和延迟增加。
- 模型更容易被噪声干扰。
- 可能超过上下文窗口限制。

选择 K 要看场景：

- 简单 FAQ：K=3 到 5 可能足够。
- 长文档问答：K=5 到 10。
- 法律、金融、科研类：可能先召回 20-50，再 rerank 到 5-10。
- 多文档综合：需要更大的初始召回和更强重排。

常见做法是：

1. 第一阶段召回较多，比如 top 30。
2. 用 reranker 精排。
3. 最终选 top 5-8 放入 Prompt。

**8. 什么是 Reranker？为什么只用向量检索还不够？**

Reranker 是对初步召回结果重新排序的模型或算法。

向量检索通常是双塔模型：

- Query 单独编码。
- Document 单独编码。
- 用向量相似度计算相关性。

它速度快，但精度有限。因为 query 和 document 没有充分交互，容易召回“语义大概相关但不能回答问题”的内容。

Reranker 通常是 cross-encoder 模型：

- 把 query 和 document 一起输入模型。
- 模型判断这个 document 是否真正能回答 query。

优点：

- 排序更准确。
- 能理解细粒度匹配。
- 能过滤掉泛相关但无用的片段。

缺点：

- 成本更高。
- 延迟更大。
- 通常只能处理几十个候选结果。

典型流程：

```text
用户问题
 -> 向量检索 top 50
 -> BM25 检索 top 50
 -> 合并去重
 -> reranker 排序
 -> 取 top 5
 -> 交给 LLM
```

**9. 什么是 Hybrid Search？为什么 RAG 常用混合检索？**

Hybrid Search 是把语义检索和关键词检索结合起来。

常见组合：

- Vector Search：基于 embedding 的语义相似度。
- BM25 / Full-text Search：基于关键词和词频的传统检索。

向量检索擅长：

- 同义表达。
- 语义相似问题。
- 自然语言查询。

关键词检索擅长：

- 错误码。
- 产品型号。
- 人名、地名、公司名。
- API 名称。
- 法律条款编号。
- 订单号、ID、SKU。

例如用户问：

```text
报错 ERR_AUTH_401 怎么解决？
```

纯向量检索可能找不到最精确的错误码文档，而 BM25 可以直接命中。

所以很多生产级 RAG 会使用：

```text
向量召回 + 关键词召回 + 元数据过滤 + rerank
```

这样召回率和精度都更稳。

**10. RAG 中如何处理权限控制？**

权限控制是企业 RAG 的关键问题。

不能简单地“所有文档全部进向量库，然后检索出来给模型”。否则可能出现越权泄露。

常见方案：

1. 索引时写入权限元数据
   每个 chunk 绑定 owner、department、tenant_id、access_group、ACL 等。

2. 检索时做权限过滤
   根据当前用户身份，只检索他有权访问的 chunk。

3. 生成前再次校验
   最终进入 Prompt 的上下文要二次检查权限。

4. 答案中避免泄露无权限来源
   如果用户无权访问相关资料，系统应回答无法访问，而不是暴露摘要。

5. 多租户隔离
   高安全场景下，不同租户可以使用不同 namespace、collection，甚至不同数据库。

6. 日志脱敏
   不要把敏感 prompt、检索内容、用户问题原样写入不安全日志。

RAG 权限的原则是：权限过滤必须发生在检索阶段之前或检索阶段中，而不是等 LLM 生成后再补救。

**11. RAG 如何减少幻觉？**

RAG 可以降低幻觉，但不能自动消灭幻觉。

常见手段：

1. 明确系统提示词
   要求模型只基于提供的上下文回答，不知道就说不知道。

2. 提供高质量检索上下文
   如果召回错误，模型很可能基于错误内容生成。

3. 加引用来源
   答案中标注来自哪些文档片段。

4. 做答案一致性检查
   让模型判断答案中的每个关键陈述是否被上下文支持。

5. 限制回答范围
   不允许模型自由发挥未检索到的内容。

6. 使用 reranker
   减少无关 chunk 进入 Prompt。

7. 做 query rewrite
   提升用户问题和文档表达之间的匹配程度。

8. 拒答机制
   当检索结果置信度低时，不强行回答。

一个常见 Prompt 约束是：

```text
如果上下文中没有足够信息，请回答“根据已提供资料无法确定”，不要编造。
```

但光靠 Prompt 不够，检索质量才是根。

**12. 如何评估一个 RAG 系统的效果？**

RAG 评估通常分两层：检索评估和生成评估。

检索评估指标：

- Recall@K：正确证据是否出现在前 K 个结果中。
- Precision@K：前 K 个结果里有多少是真相关。
- MRR：第一个正确结果排得有多靠前。
- NDCG：综合考虑相关性和排序位置。

生成评估指标：

- Faithfulness：答案是否忠实于上下文。
- Answer Correctness：答案是否正确。
- Completeness：是否覆盖问题需要的信息。
- Citation Accuracy：引用是否真的支持答案。
- Refusal Quality：不知道时是否正确拒答。
- Format Compliance：格式是否符合要求。

线上指标：

- 用户点击率。
- 追问率。
- 人工反馈。
- 答案被采纳率。
- 延迟。
- 成本。
- 无答案率。
- 投诉和纠错率。

一个好的评估集应该包含：

- 简单事实问答。
- 多文档综合问题。
- 找不到答案的问题。
- 权限边界问题。
- 易混淆问题。
- 真实用户历史问题。

**13. RAG 中 Query Rewrite 有什么作用？**

Query Rewrite 是在检索前改写用户问题，让它更适合检索。

用户问题经常很口语化、缺上下文或指代不清。

例如：

```text
用户：这个怎么开？
```

如果前文是“企业微信通知配置”，系统需要改写成：

```text
如何开启企业微信通知配置？
```

常见 Query Rewrite 类型：

- 补全上下文。
- 改写口语表达。
- 生成多个检索查询。
- 提取关键词。
- 翻译查询语言。
- 分解复杂问题。
- 将模糊问题改成文档中更可能出现的表达。

例如 Multi-query Retrieval：

```text
原问题：如何提高 RAG 准确率？
查询 1：RAG 检索召回率优化
查询 2：RAG reranker 使用方法
查询 3：RAG chunk size tuning
查询 4：RAG hallucination reduction
```

风险是：改写可能改变用户原意。所以重要场景中要保留原 query，并把多个 query 的召回结果合并。

**14. RAG 如何处理多轮对话？**

多轮对话中，用户的问题往往依赖上下文。

例如：

```text
用户：我们公司的报销标准是什么？
助手：……
用户：那出差住宿呢？
```

第二个问题单独看不完整，需要结合历史对话改写成：

```text
我们公司的出差住宿报销标准是什么？
```

常见做法：

1. Conversation-aware query rewrite
   根据历史对话把当前问题改写为独立问题。

2. 保留最近对话上下文
   将最近几轮对话放入 Prompt，但要控制长度。

3. 检索历史记忆
   对长期会话内容也可以做向量化记忆检索。

4. 避免把错误答案带入下一轮
   多轮中不能只依赖助手上一轮回答，要重新检索证据。

5. 处理指代
   如“这个”“它”“上面那个方案”需要解析。

推荐架构：

```text
当前问题 + 对话历史
 -> 生成 standalone question
 -> 检索知识库
 -> 基于检索内容回答
```

**15. RAG 对表格、PDF、图片这类复杂文档怎么处理？**

复杂文档不能简单粗暴地提取纯文本。

PDF 问题：

- 多栏排版容易乱序。
- 页眉页脚污染内容。
- 表格结构丢失。
- 扫描件需要 OCR。
- 图表信息无法直接提取。

表格问题：

- 行列关系重要。
- 单独切 chunk 容易丢上下文。
- 数值需要精确计算。

图片问题：

- 需要 OCR 或多模态模型提取。
- 图表、流程图、截图需要结构化描述。

常见处理方案：

- PDF 使用专业解析器，保留标题层级、页码、段落。
- 表格转成 Markdown table、HTML table 或结构化 JSON。
- 对大表格建立字段级索引。
- 图片走 OCR，并保存图片引用。
- 对图表生成文字摘要。
- 保留元数据，如页码、章节、表名、图号。
- 对不同文档类型使用不同 chunk 策略。

面试中可以强调：文档解析质量决定 RAG 上限。很多 RAG 效果差，不是模型差，而是数据清洗和切分差。

**16. RAG 中如何处理长文档问答？**

长文档问答常见挑战：

- 文档太长，不能全部塞进上下文。
- 问题可能涉及多个章节。
- 答案需要综合多个位置。
- 检索可能只召回局部片段。

常见方案：

1. 层级索引
   先检索章节摘要，再检索章节内部 chunk。

2. Parent-child chunk
   小 chunk 用于检索，大 chunk 或父段落用于生成。

3. Map-reduce
   先对多个片段分别回答，再汇总。

4. Recursive retrieval
   根据初步结果继续检索相关上下文。

5. 文档摘要索引
   为章节、文档生成摘要 embedding。

6. Metadata filtering
   根据文档类型、章节标题、时间范围缩小范围。

7. Sliding window
   命中某个 chunk 后，带上前后相邻 chunk。

例如：

```text
检索命中第 5 段
实际给模型：第 4、5、6 段
```

这样可以补足上下文。

**17. 为什么 RAG 会答错？常见原因有哪些？**

RAG 答错通常不是单点问题，而是链路上多个环节累积。

常见原因：

1. 数据源错误
   原始文档过期、重复、互相矛盾。

2. 文档解析错误
   PDF 乱序、表格丢列、OCR 错别字。

3. Chunk 切分不合理
   关键信息被切散或和噪声混在一起。

4. Embedding 模型不适合领域
   对专业术语、中文、代码、法律文本理解不好。

5. 检索召回失败
   正确证据没有被找出来。

6. 排序失败
   正确证据召回了，但排在后面没进入 Prompt。

7. Prompt 设计差
   模型没有被明确要求基于证据回答。

8. 上下文过长
   模型忽略中间内容或被无关内容干扰。

9. 用户问题模糊
   系统没有先澄清或改写。

10. 生成阶段幻觉
   模型超出上下文补充了未被支持的信息。

面试中可以用一句话概括：RAG 的质量瓶颈经常在“检索前的数据处理”和“生成前的上下文选择”，不是只换一个更大的模型就能解决。

**18. 如何优化 RAG 的延迟和成本？**

RAG 延迟来自多个环节：

- Query rewrite
- Embedding
- 向量检索
- 关键词检索
- Rerank
- LLM 生成
- 引用校验

优化方式：

1. 缓存
   缓存 query embedding、热门问题答案、检索结果。

2. 减少不必要的 LLM 调用
   简单问题不一定需要 query rewrite。

3. 使用轻量模型做前置任务
   小模型做 query rewrite、分类、路由。

4. 分层检索
   先粗召回，再精排，避免全量重排。

5. 控制上下文长度
   只放真正必要的 chunk。

6. 并行检索
   向量检索、关键词检索、权限过滤可以并行。

7. 使用流式输出
   改善用户感知延迟。

8. 模型路由
   简单问题用小模型，复杂问题用大模型。

9. 索引优化
   调整 HNSW、IVF 等近似检索参数。

10. 批处理
   文档入库、embedding 生成使用 batch。

成本优化的核心是：不要让大模型做所有事，能用检索、规则、小模型解决的，就不要交给最贵的生成模型。

**19. 什么是 Agentic RAG？和普通 RAG 有什么区别？**

普通 RAG 通常是固定流程：

```text
问题 -> 检索 -> 生成
```

Agentic RAG 更动态。它让模型或 agent 根据问题决定下一步动作。

可能的行为包括：

- 判断是否需要检索。
- 选择哪个知识库。
- 拆解复杂问题。
- 多次检索。
- 调用工具。
- 对检索结果反思。
- 发现证据不足后继续搜索。
- 最后综合回答。

例如用户问：

```text
对比我们 Q1 和 Q2 的销售策略变化，并给出原因。
```

普通 RAG 可能一次检索就回答。Agentic RAG 可能会：

1. 检索 Q1 销售策略。
2. 检索 Q2 销售策略。
3. 检索销售数据。
4. 对比差异。
5. 找到原因。
6. 生成结构化答案。

优点：

- 适合复杂、多步、多源问题。
- 召回更灵活。
- 能处理开放式分析任务。

缺点：

- 延迟更高。
- 成本更高。
- 结果不稳定。
- 更难评估和调试。

**20. 如果让你设计一个企业内部知识库问答 RAG 系统，你会怎么设计？**

可以从架构、安全、检索、生成、评估几个方面回答。

整体架构：

```text
数据源
 -> 文档解析
 -> 清洗去重
 -> Chunk 切分
 -> Embedding
 -> 向量库 / 搜索引擎
 -> 检索 + 权限过滤
 -> Rerank
 -> Prompt 构造
 -> LLM 生成
 -> 引用与校验
 -> 日志与评估
```

数据层：

- 接入 Confluence、飞书、Notion、Google Drive、PDF、Git 仓库等。
- 定时同步和增量更新。
- 保留文档 ID、标题、作者、更新时间、权限、版本。
- 删除或更新文档时同步更新索引。

检索层：

- 使用 hybrid search。
- 向量检索负责语义匹配。
- BM25 负责关键词、编号、术语匹配。
- 使用 reranker 精排。
- 根据用户身份做 ACL 过滤。
- 对多轮问题做 query rewrite。

生成层：

- Prompt 中明确要求基于上下文回答。
- 无证据时拒答。
- 返回引用来源。
- 对答案做格式约束，比如摘要、步骤、表格。
- 对敏感内容做脱敏和权限检查。

评估层：

- 构建黄金问答集。
- 评估 Recall@K、faithfulness、answer correctness。
- 收集用户反馈。
- 记录检索命中的文档和最终引用。
- 监控延迟、成本、错误率。

上线策略：

- 先做只读问答。
- 再支持多轮和复杂分析。
- 最后接入工具调用或自动执行能力。
- 对高风险场景保留人工确认。

面试中可以补一句：企业 RAG 的难点不只是“向量数据库 + LLM”，更重要的是权限、数据质量、持续评估和可观测性。
