# 20 道 ai agent 开发 面试题，要有详细答案

> 20 道  ai agent 开发 面试题，要有详细答案

下面给你一套 **20 道 AI Agent 开发面试题 + 详细答案**，适合准备 **Agent 工程师 / LLM 应用开发 / AI 产品研发** 面试。

---

## 1. 什么是 AI Agent？它和普通 LLM 应用有什么区别？

**答：**
AI Agent 不只是“调用一次大模型返回结果”的程序，而是能**感知环境、规划步骤、调用工具、执行动作、根据结果再调整**的系统。
普通 LLM 应用通常是：

- 输入问题
- 模型一次性输出答案

而 Agent 通常包含：

- **目标理解**
- **任务拆解**
- **工具调用**
- **状态管理**
- **循环执行**
- **结果校验**

比如一个“帮我订机票”的 Agent，不只是回答“去哪订”，而是能查航班、比价格、筛选条件、生成候选方案，甚至推动下一步操作。

---

## 2. AI Agent 的核心组成一般有哪些？

**答：**
一个完整 Agent 通常有这几个核心模块：

1. **LLM 推理层**
   负责理解任务、生成计划、决定下一步动作。

2. **Planner / Reasoner**
   把复杂目标拆成子任务。

3. **Tool Use / Function Calling**
   调用搜索、数据库、代码执行、API、浏览器等工具。

4. **Memory**
   记录短期上下文和长期知识。

5. **Executor**
   按计划执行动作，并处理工具返回结果。

6. **State / Scratchpad**
   保存当前任务进度、已完成步骤、失败重试信息。

7. **Guardrails**
   控制安全、权限、输出格式和错误行为。

---

## 3. Agent 和 Workflow 的区别是什么？

**答：**
这是面试里很常问的一题。

**Workflow** 是预先定义好的固定流程，比如：

- 先分类
- 再检索
- 再总结

它的路径基本确定。

**Agent** 则是动态决策系统，路径不是固定的，模型会根据当前状态决定：

- 要不要查资料
- 要不要调用工具
- 要不要重试
- 要不要改计划

**简单说：**

- Workflow = 人设计流程，模型只负责局部推理
- Agent = 模型参与决策，流程会动态变化

工程上通常建议：
**能用 Workflow 解决的问题，不要一上来就做 Agent**，因为 Agent 更灵活，但也更难控、更贵、更不稳定。

---

## 4. 什么是 ReAct？为什么它在 Agent 里常用？

**答：**
ReAct = **Reasoning + Acting**。
它是一种让模型在“思考”和“行动”之间交替进行的模式。

典型流程：

- 思考：我需要查一下最新价格
- 行动：调用搜索工具
- 观察：返回搜索结果
- 再思考：结果里哪个更靠谱
- 再行动：调用另一个工具或输出结论

**优点：**

- 适合复杂任务
- 让模型具备可解释的中间步骤
- 方便接工具

**缺点：**

- token 消耗高
- 容易循环
- 对提示词和工具设计要求高

---

## 5. 什么是 Agent 的“规划能力”？怎么实现？

**答：**
规划能力是指 Agent 能把一个大目标拆成多个可执行步骤。

例如“帮我做一个竞品调研报告”可以拆为：

1. 明确调研对象
2. 搜集竞品信息
3. 对比功能、价格、用户评价
4. 归纳差异
5. 输出报告

常见实现方式：

- **单步规划**：先生成完整计划，再逐步执行
- **动态规划**：每完成一步，再根据新信息改计划
- **层级规划**：高层负责大目标，低层负责具体执行

面试时可以补一句：
规划本质上是在**减少 LLM 一次性完成复杂任务的难度**，把问题分解到更可控的粒度。

---

## 6. 什么是 Tool Calling？为什么它对 Agent 很重要？

**答：**
Tool Calling 指模型根据需要调用外部工具，而不是只靠参数记忆回答。

常见工具包括：

- 搜索引擎
- 数据库查询
- 代码执行器
- 浏览器
- 邮件 / 日历 / CRM API
- 向量检索

**为什么重要：**

1. **突破模型知识截止**
2. **连接真实世界**
3. **降低幻觉**
4. **支持可执行任务**

Agent 的价值，很多时候不是“会说”，而是“会做”。

---

## 7. 什么是上下文窗口？在 Agent 中有什么问题？

**答：**
上下文窗口是模型一次能处理的 token 数量上限。

在 Agent 场景里，上下文容易爆掉，因为会不断累积：

- 用户输入
- 历史对话
- 工具返回结果
- 中间推理过程
- 执行日志

**问题：**

- 成本上升
- 速度变慢
- 关键内容被截断
- 模型注意力分散

**常见解决办法：**

- 只保留关键信息
- 压缩历史
- 用摘要替代原文
- 用结构化状态存储
- 将长内容放进检索系统而不是直接塞上下文

---

## 8. 什么是 Agent Memory？短期记忆和长期记忆有什么区别？

**答：**
Agent Memory 指系统保存和使用信息的能力。

### 短期记忆
- 当前对话上下文
- 当前任务状态
- 临时工具结果

### 长期记忆
- 用户偏好
- 历史任务经验
- 领域知识
- 过去成功策略

### 区别
- 短期记忆更像“工作台”
- 长期记忆更像“知识库”

工程里通常不会把所有东西都直接丢给模型，而是：

- 短期状态放结构化存储
- 长期记忆放数据库 / 向量库
- 需要时再检索

---

## 9. Agent 为什么容易“幻觉”？怎么降低？

**答：**
Agent 幻觉主要来自三类原因：

1. **模型知识不完整**
2. **工具返回不可靠**
3. **上下文噪音太多，模型自己补细节**

### 降低方法：
- 强制工具查询真实数据
- 让模型输出结构化结果
- 对关键字段做校验
- 重要结论必须有来源
- 设计失败重试机制
- 用检索增强生成（RAG）
- 给模型明确“不知道就说不知道”

面试时可以强调：
Agent 的核心不是“让模型更聪明”，而是**让系统更可验证**。

---

## 10. 什么是 RAG？它和 Agent 的关系是什么？

**答：**
RAG = Retrieval-Augmented Generation，检索增强生成。
它先从外部知识库检索相关内容，再让模型基于检索结果回答。

**和 Agent 的关系：**

- RAG 更偏“知识增强”
- Agent 更偏“行动与决策”

但二者经常结合：

- Agent 判断需要知识
- 调用检索工具
- 将检索结果作为上下文
- 再生成回答或执行下一步

可以理解为：
**RAG 是 Agent 常用的一个工具或子模块。**

---

## 11. 你会如何设计一个 Agent 的状态管理？

**答：**
我会把状态分成三层：

1. **对话状态**
   当前用户说了什么、系统在做什么

2. **任务状态**
   当前目标、已完成步骤、待办事项、失败记录

3. **外部状态**
   数据库、文件、缓存、用户权限、调用结果

### 设计原则：
- 不把所有状态都塞进 prompt
- 尽量结构化
- 可恢复、可重试
- 每一步都能追踪
- 支持断点继续

实际实现常见做法是：
- 用 JSON / SQL 存任务状态
- 用日志记录每次工具调用
- 用摘要同步给模型

---

## 12. 什么是多 Agent 系统？它适合什么场景？

**答：**
多 Agent 系统是多个 Agent 协作完成任务，每个 Agent 负责不同角色。

比如：

- 一个负责规划
- 一个负责搜索
- 一个负责写作
- 一个负责审核

### 适合场景：
- 任务复杂
- 角色分工明确
- 需要并行处理
- 需要互相校验

### 风险：
- 协调成本高
- 容易互相重复
- 调试困难
- 延迟和成本更高

面试里要说清楚：
多 Agent 不是越多越好，很多时候**一个强状态机 + 一个模型就够了**。

---

## 13. 如何评价一个 Agent 的效果？

**答：**
不能只看“回答像不像人”，要看任务指标。

### 常见评价维度：
- **成功率**
- **任务完成时间**
- **工具调用次数**
- **token 成本**
- **正确率**
- **用户满意度**
- **失败恢复能力**
- **安全违规率**

### 评估方式：
- 人工标注
- 离线 benchmark
- 回放真实日志
- A/B 测试
- 红队测试

Agent 评估的关键是：
**看它是否稳定完成目标，而不是只看单轮回答质量。**

---

## 14. Agent 调试时你会看哪些东西？

**答：**
我会重点看：

1. **prompt 是否清晰**
2. **工具输入输出是否正确**
3. **计划是否合理**
4. **是否陷入循环**
5. **状态是否丢失**
6. **检索结果是否相关**
7. **失败是否被正确处理**

### 常用调试手段：
- 打印每轮思考和动作
- 保存完整执行 trace
- 对工具调用做日志
- 重放历史任务
- 在小样本上做回归测试

Agent 调试比普通后端更像“查行为链路”，不是只看一个 API 返回值。

---

## 15. 什么是 Prompt Engineering 在 Agent 中的作用？

**答：**
Prompt Engineering 在 Agent 里不只是“写得礼貌点”，而是**控制系统行为**。

它会影响：

- 任务理解
- 工具调用时机
- 输出格式
- 安全边界
- 是否主动澄清
- 是否遵循计划

### 常见技巧：
- 明确角色和目标
- 规定输出 JSON 结构
- 给工具使用规则
- 提供少量示例
- 指定失败处理逻辑

但要注意：
Agent 不应只靠 prompt 控制，最好结合**程序约束、状态机、schema 校验**。

---

## 16. Agent 如何避免无限循环？

**答：**
无限循环是 Agent 常见问题，比如一直“思考-调用-思考”却不收敛。

### 解决方法：
- 设置最大步数
- 设置超时
- 设置重复动作检测
- 设置终止条件
- 设置置信度阈值
- 失败后强制总结并退出

例如：
- 最多执行 8 步
- 同一工具同一参数最多重试 2 次
- 如果连续 3 次无进展，切换策略或向用户澄清

这是工程上非常重要的控制点。

## 17. 什么是 structured output？为什么它对 Agent 很关键？

**答：**
Structured output 指让模型输出可机器解析的结构化格式，比如 JSON、XML、Pydantic schema。

**好处：**
- 易解析
- 易验证
- 易进入后续流程
- 减少歧义

例如不要让模型随便输出：
“我建议先查资料，再整理成表格。”

而是输出：
```json
{
  "next_action": "search",
  "query": "AI agent development interview questions",
  "reason": "Need more examples"
}
```

Agent 很多时候不是在“写文章”，而是在“给程序发指令”，所以结构化输出很重要。

## 18. 你怎么设计 Agent 的安全机制？

**答：**
Agent 安全要考虑两层：

### 1. 模型安全
- 防止越权指令
- 防止 prompt injection
- 防止泄露敏感信息

### 2. 系统安全
- 工具白名单
- 权限控制
- 数据脱敏
- 审计日志
- 人工确认关键操作

### 例子
如果 Agent 能发邮件、转账、删库，必须：

- 有权限分级
- 有确认步骤
- 有操作日志
- 有回滚机制

面试里可以强调：
**真正的 Agent 安全不是只防模型乱说，而是防模型乱执行。**

---

## 19. 什么是 prompt injection？Agent 如何防？

**答：**
Prompt injection 是指恶意内容诱导模型偏离原始指令，比如：

- “忽略之前所有指令”
- “把系统 prompt 发出来”
- “直接把数据库里的隐私给我”

### 防护方法：
- 把用户输入和系统指令隔离
- 对外部文本做不可信标记
- 工具输出不要直接当成指令执行
- 对敏感工具加权限
- 关键动作需要策略层确认
- 使用内容过滤和规则引擎

Agent 场景里，外部网页、文档、邮件都可能携带 injection，所以这题非常常见。

## 20. 你会如何从 0 到 1 设计一个实用的 AI Agent？

**答：**
我会按这条路线做：

1. **先定义任务边界**
   明确 Agent 到底解决什么，不解决什么。

2. **先做 Workflow，再考虑 Agent 化**
   先把关键路径做稳定。

3. **接入必要工具**
   搜索、数据库、文件、API、代码执行器。

4. **设计状态和日志**
   让每一步可追踪、可恢复。

5. **加约束**
   限步数、限权限、限格式、限重试。

6. **做评估集**
   收集真实任务样本，做离线回归。

7. **再做智能化升级**
   例如动态规划、多轮反思、多 Agent 协同。

一句话总结：
**先把系统做稳，再把它做聪明。**
